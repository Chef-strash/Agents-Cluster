1. DISTRIBUTED WORKLOADS ACROSS MULTIPLE PHYSICAL SYSTEMS
--------------------------------------------------------------------------------
Q: What were the physical systems? How did they communicate?
• Architecture Setup:
  - System Count: 2–3 physical machines (e.g., primary development laptop, secondary PC, or local VM).
  - Operating Systems: Windows / Linux machines running Python 3.10+.
  - Network Topology: Hub-and-Spoke model over local network or WAN (using Ngrok secure tunnels to cross NAT/firewalls).
  - Communication Protocol: The central machine runs the FastAPI Broker server. Remote machines run Subagent worker scripts (`subagent/app.py`) that establish outbound WebSocket connections (`wss://`) back to the Broker.

--------------------------------------------------------------------------------
2. EXPERIMENTAL TIME REDUCTION (MEASUREMENT & BENCHMARKING)
--------------------------------------------------------------------------------
Q: How did you measure the 65% reduction in execution time?
• Baseline (Sequential Execution):
  - Running 6 LLM subagent tasks sequentially on a single node took ~180 seconds (~30 seconds per LLM response).
• Parallel/Distributed Execution:
  - Distributing the same 6 subagent tasks in parallel across worker nodes reduced total completion time to ~62 seconds (governed by the single slowest worker rather than the sum of all workers).
• Measurement Methodology:
  - Timed across 30 experimental runs using standard Python timing utilities (`time.perf_counter()`), measuring wall-clock time from task distribution (`/distribute`) to full response aggregation.

--------------------------------------------------------------------------------
3. DISTRIBUTING REQUESTS ACROSS MULTIPLE API KEYS / PROVIDERS
--------------------------------------------------------------------------------
Q: Why multiple API keys/models and how were requests routed?
• Motivation:
  - To prevent rate limiting (HTTP 429 errors) and maximize throughput during high-concurrency multi-agent rounds.
• Routing & Fallback Logic:
  - Local Offloading: Using local Ollama LLM instances (`qwen2.5:1.5b`) on worker nodes to reduce cloud API calls completely.
  - Retry & Backoff: Subagents implement exponential backoff retry loops (`subagent/app.py`) with 3-second sleep intervals when encountering rate limits or transient network errors.
  - Worker-Level Isolation: Each subagent runs independently; if one API key hits a rate limit, other workers continue running.

Q: Explain and draw the Hub-and-Spoke architecture.
• Diagram:

                | LangGraph           |

                           v

  - Spokes: Workers establish persistent WebSocket streams to receive tasks and return results.
  - Coordinator: The LangGraph Orchestrator triggers execution rounds via HTTP POST to `/distribute`.

6. AGGREGATING RESPONSES & HANDLING WORKER FAILURES
--------------------------------------------------------------------------------
Q: What happens if one agent fails or lags while others finish quickly?
• Synchronization Mechanism:
  - `broker.py` uses an `asyncio.Event()` (`response_event`) to non-blockingly pause `/distribute` until responses arrive.
• Disconnect & Lag Handling:
  - If a worker crashes or drops connection, FastAPI catches `WebSocketDisconnect`, removes the agent from `broker_state.connections`, and re-evaluates response completeness.
  - If remaining online agents have submitted responses, `broker_state.response_event.set()` triggers immediately so the system doesn't hang indefinitely waiting for a dead node.
  - Subagent Retries: Workers encapsulate model calls inside try-except loops with 3 retries before returning an explicit error string.

7. LANGGRAPH ORCHESTRATION & REQUEST LIFECYCLE
--------------------------------------------------------------------------------
Q: Why LangGraph over plain asyncio? Explain the request lifecycle.
• Why LangGraph:
  - State Management: Maintained state schema (`AgentState`) across multi-round execution loops.
  - Cyclical Routing: Conditional edges (`should_continue`) enable multi-round reasoning loops (e.g. repeat up to 10 rounds).
  - Clean Abstraction: Decouples high-level orchestrator logic from low-level networking code.

• Graph Nodes:
  - `Central`: Increments `Round_No` and formats `Public_Message`.
  - `Broker`: Executes async HTTP request to `/distribute`, gathers agent responses, and appends them to `MessagePool`.

• Complete Request Lifecycle:
  1. Client starts execution -> `orchestrator_app.invoke(initial_state)`
  2. `Central` node increments round & prepares `Public_Message`.
  3. `Broker` node sends HTTP POST to `http://127.0.0.1:8000/distribute`.
  4. FastAPI Broker broadcasts payload to connected Subagents over WebSockets.
  5. Subagents process task asynchronously via `subagent_app.ainvoke()` (calling Ollama/LLM).
  6. Subagents send JSON responses back over WebSocket (`ws.send`).
  7. Broker collects responses into `broker_state.responses` and triggers `response_event`.
  8. `/distribute` HTTP endpoint completes and returns JSON to Orchestrator.
  9. `Broker` node appends results to `MessagePool` in `AgentState`.
  10. Conditional Edge checks `Round_No < 10` -> loops back to `Central` or terminates at `END`.

8. NETWORKING: WEBSOCKETS, REST, NGROK, AND ASYNCIO
--------------------------------------------------------------------------------
Q: Why WebSockets instead of REST? Why Ngrok? Which asyncio primitives?
• WebSockets vs. REST for Workers:
  - WebSockets provide persistent, full-duplex communication. Subagents behind local routers/firewalls establish ONE outbound connection to the Broker, allowing the Broker to push tasks instantaneously without polling.
• Why Ngrok:
  - Exposes the local FastAPI Broker port (8000) securely over HTTPS/WSS so remote worker nodes on different networks can connect without complex router port forwarding.
• Ngrok Challenges:
  - Tunnel instability, changing public URLs on restart, latency overhead.
• Asyncio Primitives Used:
  - `asyncio.Event()`: Gates `/distribute` HTTP response until all subagent responses arrive.
  - `asyncio.sleep()`: Used for retry backoffs.
  - `asyncio.run_coroutine_threadsafe()`: Bridges sync LangGraph node functions with async HTTPX requests.

9. SCALING & FAULT TOLERANCE
--------------------------------------------------------------------------------
• Bottlenecks at 500 Agents (Current Architecture Limits):
  1. Single-Process In-Memory Bottleneck:
     - All connections (`broker_state.connections`) and results are stored in a single Python process's RAM. Python's GIL and event loop will struggle to handle simultaneous JSON serialization/deserialization for 500 active WebSocket streams.
  2. Single Point of Failure (SPOF):
     - If the central `broker.py` process crashes or restarts, all 500 WebSocket connections drop simultaneously, losing all in-flight state.
  3. Sequential Broadcast Delay (O(N) Fan-out):
     - Iterating through 500 WebSockets sequentially (`for agent_id, websocket in connections... await send_json`) creates network latency overhead before task #500 even receives its instruction.
  4. HTTP Request Timeout:
     - The `/distribute` HTTP connection stays open waiting for all 500 agents (`await response_event.wait()`). Intermediary proxies (Ngrok/Load Balancers) will hit HTTP 504 Gateway Timeouts (usually 30–60s) while waiting.
  5. All-or-Nothing Synchronization (Straggler Problem):
     - Requiring `len(responses) >= len(connections)` means if 1 out of 500 agents lags or drops silently, the entire cluster round hangs.

• Realistic Scaling Improvements (3rd-Year Student Level):
  1. Parallel Task Broadcasting (`asyncio.gather`):
     - Instead of looping through 500 agents sequentially (`for ws in connections: await ws.send()`), use `asyncio.gather` to send task payloads to all 500 agents in parallel concurrently.
  2. Round Timeouts & Partial Completion:
     - Wrap the response wait in a timeout (`asyncio.wait_for(response_event.wait(), timeout=30)`). If 470 out of 500 agents respond within 30 seconds, proceed with the 470 results instead of letting 1 slow agent stall the whole system.
  3. Shared Key-Value Cache (Redis):
     - Replace the raw Python dictionary (`self.responses`) with **Redis** (an external key-value database).
     - *Why:* Storing data in Python RAM means if `broker.py` crashes, all collected responses are lost. Storing in Redis (`redis.set(agent_id, response)`) ensures responses survive broker crashes and can be accessed across multiple broker instances.
  4. Worker Chunking / Batching:
     - Instead of blasting 500 WebSocket messages at the exact same millisecond, send tasks in batches of 100 using `asyncio.gather` with a tiny 50ms pause between batches.
     - *Why:* Prevents network socket buffer congestion and packet drops caused by 500 simultaneous socket writes (like boarding a plane in groups rather than everyone charging the gate at once).

• Coding Question Answer (First Successful Result Pattern):
  ```python
  import asyncio

  async def worker(worker_id, delay, should_fail=False):
      await asyncio.sleep(delay)
      if should_fail:
          raise ValueError(f"Worker {worker_id} failed")
      return f"Result from worker {worker_id}"

  async def run_first_successful():
      tasks = [
          asyncio.create_task(worker(i, delay, fail))
          for i, (delay, fail) in enumerate([(3, True), (1, False), (2, False)])
      ]
      
      for completed in asyncio.as_completed(tasks):
          try:
              result = await completed
              # Cancel remaining tasks
              for t in tasks:
                  if not t.done():
                      t.cancel()
              return result
          except Exception:
              continue
  ```

10. DESIGN IMPROVEMENTS (FUTURE RETROSPECTIVE)
--------------------------------------------------------------------------------
Q: Looking back, what would you improve in this system?
• Timeouts & Fallbacks: Add per-agent execution timeouts so if one agent gets stuck, the system doesn't wait indefinitely.
• Shared Memory Storage: Use **Redis** as a simple key-value store instead of storing state in raw Python dictionaries (`BrokerState`).
• Better Error Handling & Retries: Implement explicit retry logic with exponential backoff on the worker side for network drops.
• Basic Authentication: Add API keys or tokens so only authorized workers can connect to the broker's WebSocket.
• Worker Containerization: Use **Docker / Docker Compose** so spinning up new subagent workers on any machine requires just one simple command (`docker compose up`).
